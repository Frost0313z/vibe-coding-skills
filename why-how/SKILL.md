# Why · How 개념 정리 — 왜 쓰나, 언제 쓰나

**약속 하나:** 개념마다 "그게 뭔가"보다 **"왜 쓰나"와 "언제 쓰나"**를 먼저 답한다. 예시는 지어내지 않고, 읽는 사람이 직접 짠 코드에서 찾아 붙인다.

## 1. 범위를 정한다

- 정리할 개념 목록을 확인한다. 사용자가 붙여 준 목록(예: 과제 목표의 "설명할 수 있다" 줄)이 있으면 **그 목록이 곧 차례**다. 빼거나 덧붙이지 않는다.
- 목록이 길면 영역 하나(예: "Python 기초", "클래스와 객체")를 문서 하나로 만든다. 한 문서에 여러 영역을 섞지 않는다.
- 이미 같은 형식으로 만든 문서가 있으면 읽고 **같은 형식 · 같은 말투**를 따른다.

## 2. 코드를 끝까지 읽는다

- 이 개념들이 쓰인 프로젝트 코드를 **처음부터 끝까지** 읽는다. 일부만 보고 예시를 고르지 않는다.
- 개념마다 실제로 쓰인 곳(파일 · 함수 · 변수 이름)을 찾아 적어 둔다. 좋은 예시의 기준:
  - 읽는 사람이 **알아볼 수 있는 곳**(메뉴 · 채점처럼 화면에서 본 기능)
  - **대비가 되는 쌍**(for 와 while, 속성과 임시 변수처럼 같은 코드 안에 둘 다 있는 것)
- 코드에 그 개념이 없으면 일반 예시를 쓰되 **"이 프로젝트에는 없음"**이라고 밝힌다.

## 3. 개념마다 같은 틀로 쓴다

````markdown
## N. 개념 이름

한 줄 정의. (필요하면 3~5줄짜리 코드)

### Why — 왜 쓰나

- **굵은 한 마디.** 이게 없으면 무엇이 곤란한지 한두 문장.   ← 2~3개
- (가능하면) "이게 없으면 이렇게 된다" 짧은 대조 코드

### How — 언제 쓰나

| 상황 | 무엇을 쓰나 | 내 코드 |
|---|---|---|
| …할 때 | … | `실제 이름` — 무엇을 하는지 |

(고르는 질문 하나: "목록에 든 걸 하나씩?" → for 같은 판단 기준)

### 자주 나오는 문제   ← 있을 때만

질문 → 답 한 줄.

### 시험 한 줄 답

> 왜 쓰는지 한 문장. 언제 쓰는지 한 문장.
````

- **Why**는 "무엇이 곤란해지나"로 쓴다. 정의를 다시 말하지 않는다.
- **How**는 "상황"으로 시작한다. "~할 때" 꼴로 써서 읽는 사람이 자기 상황에 대 볼 수 있게 한다.
- **헷갈리는 쌍**(list/dict, if/elif, 속성/임시 변수, 함수/메서드)은 고르는 질문 하나로 가른다.
- 맨 끝에 **「한눈에 보기」 표**(개념 | Why | How)를 단다. 시험 직전엔 이 표만 봐도 되게.

## 4. 문서 규칙

- 읽는 사람은 비개발자 · 초보다. 쉬운 말로, 영어 약어는 처음 한 번 풀어 쓴다.
- **원시 HTML(`<details>` 등)을 넣지 않는다.** 표 · 인용 · 코드 블록만.
- 파일은 프로젝트의 `docs/<영역>-왜와-언제.md` (공백 대신 `-`). `docs/` 가 없으면 만들기 전에 위치를 묻는다.
- 맨 위에 "무엇을 두 질문으로 나눴는지"와 "예시는 어느 파일에서 가져왔는지"를 적는다.

## 5. 확인한다 — 잰 것만 적는다

- 문서에 적은 **함수 · 변수 · 코드 줄을 모두 검색해 실제 코드와 대조**한다. 이름이 하나라도 다르면 고친다.
- 계산 결과를 적었으면(예: `round(2 / 3 * 100)` → `67`) **실제로 돌려 본** 값을 적는다.
- "자주 나오는 실수" 코드는 정말 그 오류가 나는지 돌려 볼 수 있으면 돌려 본다.

## 6. 보고한다

- 만든 파일 경로와 절 목록.
- **가장 헷갈리기 쉬운 곳 하나**를 짚어 준다(예: "속성이냐 임시 변수냐").
- 코드에서 요구사항과 어긋난 곳을 봤으면 고치지 말고 알린다.
- 커밋은 사용자가 말할 때만. 다음 영역도 같은 형식으로 만들지 한 번 묻는다.

## 같이 쓰면 좋은 것

- 정리한 뒤 실전 연습 → 한 문제씩 내고 답을 듣는 문답(질문은 한 번에 하나).
- 답 없이 질문만으로 본질을 파고들려면 `socratic`.
