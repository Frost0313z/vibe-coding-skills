# 리팩토링 — 겉은 그대로, 속만 정리

**약속 하나:** 사용자가 보는 화면 · 함수의 결과는 고치기 전과 같다. 같다는 것을 **재서** 보인다. 동작을 바꿔야 하는 문제(버그)를 찾으면 고치지 말고 따로 알린다.

## 1. 범위를 한 문장으로

- 무엇을(파일 · 화면 · 기능) 정리하는지 한 문장으로 확인한다. "전체적으로"라고 하면 그 영역 안에서 위험이 낮은 것부터 한다.
- 지금 브랜치를 본다. 기본 브랜치(main)이면 새 브랜치를 먼저 판다. 프로젝트 규칙(CLAUDE.md · 담당 폴더 · 커밋 규칙)이 있으면 그것을 따른다.

## 2. 끝까지 읽는다

- 대상 코드를 **처음부터 끝까지** 읽는다. 일부만 보고 고르지 않는다.
- 고칠 함수 · 변수마다 **부르는 곳을 모두 찾는다**(코드 · 화면 HTML · 시험 파일까지). 부르는 곳이 0이면 죽은 코드 후보다.
- 이 코드를 확인하는 시험을 찾는다. 시험이 글자 모양(정규식)으로 코드를 보고 있으면, 고친 뒤 그 시험도 같은 뜻으로 맞춰야 한다.

## 3. 후보를 근거와 함께 고른다

| 후보 | 근거로 볼 것 |
|---|---|
| 죽은 코드 | 정의만 있고 부르는 곳 0 — 찾은 검색을 그대로 보인다 |
| 반복 | 같은 HTML · 같은 계산을 여러 곳에서 따로 쓴다 — 몇 곳인지 센다 |
| 같은 일 · 다른 구현 | 이름이 같은데 내용이 조금씩 다르다(빠진 처리가 있으면 그건 버그 후보로 따로 알린다) |
| 낡은 주석 | 지운 기능 · 바뀐 동작을 말하는 주석, 같은 말을 되풀이하는 주석 |
| 너무 큰 덩어리 | 줄 수 · 함수 수를 잰다. **나누기는 위험이 커서 먼저 묻는다** |

- 고르지 않은 것도 이유와 함께 적는다(예: "담당이 다른 폴더라 · 시험 기간이라 미룸").
- 위험이 큰 것(파일 나누기, 여러 파일에 걸친 이름 바꾸기, 남이 맡은 영역)은 하지 말고 묻는다.

## 4. 고치기 전에 기준선을 떠 둔다

같다는 것을 비교할 재료를 **고치기 전에** 만든다.

- **화면이면** 대상 영역의 HTML을 상태별로(모드 · 펼침/접힘 등) 떠서 파일로 둔다. 태그 사이 공백만 줄이고, 시간처럼 매번 바뀌는 글은 자리표시로 바꾼다. **두 번 떠서 같은지** 먼저 확인한다 — 다르면 기준선으로 쓸 수 없다.
- **함수면** 입력 몇 개와 그 출력을 표로 떠 둔다(경계값 포함).
- 기존 시험이 통과하는지 먼저 돌린다. 원래 실패하던 시험은 이름을 적어 두고, 고친 뒤 "원래부터 실패"인지 되돌려 비교해 가린다.

## 5. 고친다 — 한 묶음씩

- 문자열 치환은 **정확히 한 곳만 맞는지** 확인하며 한다(맞는 곳이 0 · 2 이상이면 멈춘다).
- 도우미를 만들면 기존 이름 · 모양(글자, 속성 순서, 빈칸 처리)을 그대로 낸다. 줄이 줄었다고 끝이 아니라 출력이 같아야 끝이다.
- 기능을 더하지 않는다. 고치다 보이는 버그 · 더 나은 문구는 메모만 하고 보고에 넣는다.
- **되돌릴 때 `git checkout -- <파일>` · `git restore`를 쓰지 않는다** — 고친 것까지 날아간다. 실험은 사본 파일로 하고, 되돌릴 때는 미리 떠 둔 사본에서 가져온다.

## 6. 확인한다 — 잰 것만 말한다

1. 문법 검사(예: `node --check`).
2. **기준선 비교** — 4에서 뜬 것과 한 글자까지 같은지. 다르면 첫 다른 자리 앞뒤를 보이고 고친다.
3. 전체 시험. 화면을 실제 브라우저로 누르는 시험(e2e)이 건너뛰어지면 따로 돌릴 방법을 찾는다.
4. 화면이면 눈으로 본다(스크린샷).

## 7. 보고한다

- 무엇을 왜 모았나/지웠나, 줄 수 변화(+/−).
- 확인 결과와 **잰 날짜** — 기준선 비교 결과, 시험 수, 원래부터 실패하던 것.
- **확인 못 한 것** — 기준선에 없던 상태(그 상태는 코드 읽기로만 같다고 봤다는 것까지).
- 남은 후보와 하지 않은 이유. 커밋 · PR은 사용자가 말할 때만.

## 같이 쓰면 좋은 것

- 과하게 만든 코드만 골라 보려면 `ponytail-review` · `ponytail-audit`.
- 동작이 틀린 곳(버그)은 리팩토링이 아니다 — `/code-review`로 따로 본다.
