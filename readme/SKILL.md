# 리드미 — 남에게 설명하는 첫 문서

**약속 셋:** ① 처음 보는 사람이 **3분 안에** "무엇인지 · 왜 만들었는지 · 어떻게 돌리는지"를 안다. ② 적힌 이름 · 명령 · 숫자 · 화면은 **전부 코드와 실행으로 확인한 사실**이다 — 없는 기능, 가짜 수치, 지어낸 화면을 넣지 않는다. ③ 마크다운에 원시 HTML(details · img · br 같은 태그)을 넣지 않는다 — 편집기가 렌더를 포기한다.

## 1. 읽는 사람을 정한다

- 누가 읽나 한 줄로 정한다 — 과제 심사자 / 동료평가 상대 / 이어받을 개발자 / 사용자.
- **과제 · 공모전이면 요구 항목이 곧 뼈대다.** PRD · 미션 문서 · 심사 기준에서 README 에 들어가야 할 항목을 먼저 뽑아 목차에 그대로 넣는다(빠뜨리면 감점).
- 기존 README 가 있으면 끝까지 읽고, 맞는 내용은 살린다.

## 2. 재료를 모은다 — 읽고, 돌리고, 잰다

| 재료 | 얻는 방법 |
|---|---|
| 하는 일 · 기능 | 코드를 **끝까지** 읽는다. 메뉴 · 라우트 · 명령 · 공개 함수 목록을 뽑는다 |
| 실행 방법 · 버전 | 실제로 돌려 본다(`python --version`, `npm run dev` 등). 필요한 설치 명령도 직접 확인 |
| 실행 화면 | **실제 출력**을 떠서 쓴다. 랜덤 · 시간처럼 매번 바뀌는 값은 고정하거나 예시라고 밝힌다 |
| 파일 구조 | `git ls-files` 로 저장소에 실제로 있는 파일만 |
| 데이터 · 설정 | 데이터 파일 · 환경 변수의 모양(스키마), 위치, 언제 바뀌는지. **비밀값은 이름만, 값은 절대 적지 않는다** |
| 왜 이렇게 했나 | PRD · ADR · 결정 기록 · 커밋 메시지에서 "이유"를 찾는다. 사람이 정한 이유는 그 사람 말 그대로 옮긴다 |

- 실행하다가 데이터 파일(`state.json` · DB 등)이 바뀌면 **쓰기 전에 되돌린다.** 임시 폴더 사본에서 돌리는 것이 가장 안전하다.
- 모르는 것(선정 이유 · 대상 사용자 등)은 지어내지 말고 한 가지씩 묻는다.

## 3. 첫 화면 — 스크롤 전에 붙잡는다

읽는 사람은 첫 화면에서 계속 읽을지 정한다. `---` 구분선 위까지를 **후킹 구역**으로 따로 만든다. 이 구역만 읽어도 무엇인지, 왜 재밌는지, 어떻게 켜는지 알 수 있어야 한다.

| 순서 | 넣을 것 | 요령 |
|---|---|---|
| 1 | 제목 + 이모지 하나 | 주제를 떠올리게 하는 이모지 하나만 (예: 🐾) |
| 2 | **굵은 한 줄 소개** | 기능 나열 말고 **구체적인 장면 · 결과**로. 예: "흰긴수염고래부터 치타까지 — 풀고, 만들고, 최고 점수에 도전" |
| 3 | 배지 3~6개 | shields.io. 버전 · 의존성 수 · 데이터 · 출처처럼 **사실만**. 한글은 퍼센트 인코딩(`urllib.parse.quote`) |
| 4 | 대표 장면 | 스크린샷이 저장소에 있으면 그것. 없으면 **실제 출력 중 가장 극적인 순간**(틀림 → 결과 → 기록 갱신 같은)을 코드 블록으로. 줄인 곳은 `⋮` |
| 5 | 이모지 기능 표 4줄 | 머리가 빈 표(`\| \| \|`). 왼쪽 "이모지 **이름**", 오른쪽 "그래서 뭐가 좋은지" 한 줄 |
| 6 | 30초 시작 | 복사해서 붙이면 되는 명령 3줄. `&&` 로 잇지 않는다(Windows PowerShell 5.1 에서 안 됨) |
| 7 | 출처 한 줄 → `---` | 과제 · 미션 이름 같은 배경은 맨 끝에 한 줄로 |

- 가운데 정렬 · 그림 갤러리 표는 HTML 이 필요해서 쓰지 않는다(약속 ③). 사람이 이 README 만 HTML 을 허락하면 그때만.
- 후킹 구역은 본문을 **요약**할 뿐이다. 본문에 없는 기능 · 숫자를 여기서 처음 말하지 않는다.

## 4. 본문은 이 순서로 쓴다

1. **제목 + 한 줄 소개** — 3장의 후킹 구역이 이 자리를 맡는다.
2. **개요** — 누가 · 무엇을 · 왜. 글머리표 3~5개.
3. **주제 · 만든 이유**(있으면) — 사람이 정한 말 그대로.
4. **빠른 시작** — 복사해서 그대로 붙이면 돌아가는 명령 3~5줄(clone → 설치 → 실행). 필요한 버전을 명령 위에.
5. **기능 표** — `기능 | 설명` 표. 공통 규칙(입력 검사 · 오류 처리 · 저장 시점)은 표 아래 글머리표로.
6. **실행 화면** — 실제 출력 코드 블록, 또는 스크린샷(파일이 저장소에 **있을 때만**).
7. **구조** — 폴더 트리(줄마다 `# 역할` 주석) + 핵심 클래스 · 모듈 표. 흐름이 복잡하면 화살표 그림 하나(ASCII 또는 mermaid).
8. **데이터 · 설정** — 위치 · 역할 · 예시 · 키 규칙 표 · 문제가 생겼을 때 동작.
9. **설계 결정**(있으면) — `결정 | 이유` 표. 여기서 "리치함"이 나온다.
10. **개발 기록** — 브랜치 · PR 방식, 커밋 규칙, 더 자세한 문서 링크.
11. **한계 · 준비 중** — 안 되는 것을 정직하게.

과제 요구 항목은 위 순서 안에 끼워 넣되, **요구 문서의 이름 그대로** 제목을 단다(심사자가 찾기 쉽게).

## 5. 쉽게 쓰는 규칙

- 한 문장에 한 생각. 문단은 3줄을 넘기지 않는다.
- 영어 약어 · 전문 용어는 처음 나올 때 한 번 풀어 쓴다 — 예: PR(Pull Request, 병합 요청).
- 비교 · 목록은 표로. 순서가 있으면 번호, 없으면 글머리표.
- 기능마다 "왜"를 반 줄 붙인다 — 예: "바로 저장합니다(갑자기 꺼져도 남도록)".
- 코드 블록은 **복사해서 그대로 동작**해야 한다. 자리표시가 필요하면 `{저장소 주소}`처럼 눈에 띄게.
- 숫자에는 기준을 붙인다 — 예: "커밋 18개 (2026-11-11 기준)".

## 6. 확인한다 — 잰 것만 "확인함"

1. **이름 대조** — README 에 적은 함수 · 메서드 · 파일 이름을 코드와 `grep` 으로 맞춰 본다(빠진 것 · 없는 것 0).
2. **명령 대조** — 빠른 시작 명령을 새 폴더(임시 clone)에서 그대로 돌려 본다.
3. **링크 · 그림** — 상대 경로 링크와 이미지 파일이 실제로 있는지 본다. 깨진 그림 자리는 만들지 않는다.
4. **HTML 0** — `grep -c "<[a-z]" README.md` 가 0.
5. **렌더 확인** — GitHub 에서 어떻게 보이는지(PR 의 Files changed, 또는 `gh` 로 미리보기). 못 봤으면 "확인 못 함"이라고 적는다.
6. **후킹 구역** — 배지 주소마다 `curl -s -o /dev/null -w "%{http_code}"` 로 200 인지, 대표 장면의 줄마다 실제 실행 출력에 그대로 있는지(`grep -F`) 본다.
7. 실행으로 바뀐 데이터 파일이 없는지 `git status` 로 마지막 확인.

## 7. 보고한다

- 목차(무엇을 넣었나) — 표 한 장.
- 확인한 것 · 날짜, 확인 못 한 것.
- 사람이 채워야 할 빈칸(이유 · 스크린샷 등)과 언제까지.
- 커밋 · PR 은 시킬 때만(`ship`).

## 하지 않는 것

- 구현되지 않은 기능을 있는 것처럼 쓰기, 가짜 배지 · 가짜 수치 · 만든 화면.
- 자동 생성 문서를 손으로 고치기(생성기나 원본을 고친다).
- README 를 쓰려고 코드를 고치기 — 고칠 게 보이면 고치지 말고 보고에 적는다.
